# ZeusOpen v3 框架不足 — 优先级排序（P0 → P3）

> 按对日常使用的阻塞程度、数据风险、维护成本综合排序。

---

## 🔴 P0 — 阻塞级（不做会系统瘫痪或数据丢失）

| # | 不足 | 理由 |
|---|------|------|
| 1 | **任务无超时/死锁检测** | 子 Agent 一旦 hang 住或死循环，worker slot 被永久占用，整个 wave 卡住无法推进。需框架级 watchdog |
| 2 | **缺少 graceful shutdown** | 收到 SIGTERM/SIGINT 时，正在运行的子进程和 task 状态可能直接丢失，state.db 与实际情况不一致 |
| 3 | **State Store 连接池隐患** | SQLite/Postgres 高并发下连接可能打满或锁竞争，导致 API 无响应、调度器假死 |
| 4 | **Worker 资源无隔离** | 3 个 worker 同时跑时互相抢占 CPU/内存，可能导致 OOM 或系统级卡顿 |

---

## 🟠 P1 — 高优先级（严重拖慢效率或埋下技术债）

| # | 不足 | 理由 |
|---|------|------|
| 5 | **缺少任务取消/抢占** | 发现 task 跑歪了只能干等，无法中途优雅 kill，调试和迭代成本极高 |
| 6 | **API Server 单体化** | `server.py` 854 行，路由/模型/Control Plane 全挤一起，加新功能越来越痛苦 |
| 7 | **Agent 上下文无管理** | 长任务中子 Agent 上下文无限膨胀，Kimi 2.6 浪费 token，最终可能触发上下文截断 |
| 8 | **框架代码残留（业务项目）** | Factory_ERP 等业务的 `.zeus/v3/scripts/` 与 zeus-open 框架代码重复，两边不同步，bug 难以追溯 |
| 9 | **调度算法健壮性** | DAG 循环依赖检测、wave 间死锁、优先级抢占机制缺失，复杂项目容易调度异常 |
| 10 | **EventBus 无持久化** | 服务器重启后未消费事件全部丢失，Dashboard 实时状态断档 |

---

## 🟡 P2 — 中优先级（影响体验但可 workaround）

| # | 不足 | 理由 |
|---|------|------|
| 11 | **Dashboard 缺少实时日志流** | SSE 只推事件，看不到 Agent stdout/stderr，debug 时需要去 workspace 翻文件 |
| 12 | **Dashboard 缺少批量操作** | 不能批量重试、批量标记完成，wave 级别操作时效率低 |
| 13 | **缺少中间件层** | 无认证、无限流、无结构化请求日志，暴露公网有风险 |
| 14 | **配置管理简陋** | 无环境变量覆盖、无配置校验、无热重载，部署时容易配错 |
| 15 | **假设清单（assumptions.md）无人消费** | 子 Agent 写了假设，但主 Agent/调度器没有自动读取和决策的机制 |
| 16 | **PROMPT.md 膨胀** | 即使加了 Token 约束，每次会话仍注入 130+ 行提示词，长期看可进一步精简 |
| 17 | **缺少数据库迁移自动化** | Alembic 存在但不确定是否在启动时自动运行，schema 变更容易遗漏 |

---

## 🟢 P3 — 低优先级 / 锦上添花

| # | 不足 | 理由 |
|---|------|------|
| 18 | **Metrics 粒度粗** | 缺少 per-task 耗时分布、Agent 阶段细分指标，影响性能调优 |
| 19 | **Graph 可视化交互弱** | Workflow DAG 复杂时，echarts 静态渲染难以交互式排查依赖关系 |
| 20 | **Docker 镜像过大** | `python:3.13-slim` + 全量代码，可以分层构建减小体积 |
| 21 | **缺少审计日志** | task 状态变更、quarantine、retry 无不可篡改记录，追溯困难 |
| 22 | **API 版本控制缺失** | `/api/v1/` 前缀设计未做，未来 Breaking Change 时迁移成本高 |
| 23 | **缺少 Agent 沙箱** | 子 Agent 误操作 `rm -rf /` 无真正防护（目前仅靠 git worktree 隔离） |

---

## 建议的推进节奏

```
Sprint 1（本周）：P0 全做  → 系统稳定性基线
Sprint 2（下周）：P1 #5-8  → 效率提升 + 技术债遏制
Sprint 3（下下周）：P1 #9-10 + P2  → 调度健壮 + 体验打磨
Sprint 4+：P3 挑着做     → 长期优化
```

> 以上排序基于当前使用场景（Kimi CLI + ERP 项目开发）。如果你有其他实际遇到的阻塞点，优先级可以动态调整。
